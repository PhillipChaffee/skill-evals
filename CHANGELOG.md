# Changelog

## Unreleased

- New check `agent_dispatched`: `agent`, `min` (default 1), `max`, `briefMatches`, `flags`, `briefWindow` (default 400) and `modelMatches`. It counts `subagent` calls whose dispatch type, with any plugin prefix dropped, is the agent; a dispatch of no type or of `general-purpose` also counts when its brief has a line `name: <agent>` or holds the name as a whole word in its first `briefWindow` characters, and the result's reason says `matched by type` or `matched by inlined definition`. Each `subagent` call records `dispatch: { type, model, effort }` where the stream shows them (Claude Code: `subagent_type`, `model`, `effort`; null elsewhere), and a run record gains `agentTokens`, tokens by agent id summed from per-message usage (Claude Code; null elsewhere; `tokens` is unchanged). Changed on purpose: an agent that a dispatch names now counts as having run, so `tool_not_called` or `tool_called` with `max: 0` and `by: { "agent": "X" }` passes for a dispatched agent that produced no events and still fails for a typo or an inlined `general-purpose` dispatch. A matcher key `dispatches: "<agent>"` (also a field of `tool_called` and `tool_not_called`) fits a `subagent` call by the same rule, so `sameTurn`, `min`, `max`, `tool_order`, `first_tool` and `ignoring` can name dispatches by agent and not by raw JSON. New example: `examples/cases/agent-dispatched`.
- Every transcript event and tool call now carries the agent that produced it: `agent: { id, type, parent, depth }`, with `{ "id": "main", "type": "main", "parent": null, "depth": 0 }` for the main thread. On Claude Code, an event with a `parent_tool_use_id` belongs to the agent that the dispatch call of that id started; its `type` is the dispatch's `subagent_type` with any plugin prefix dropped (`general-purpose` when it names none), its `parent` is the dispatching agent, and its `depth` follows the chain (a dispatch and its result belong to the dispatcher, a parent id with no known dispatch gives type `unknown`). Every matcher and `skill_loaded`, `skill_not_loaded`, `transcript_matches` and `transcript_lacks` take `by`: `"main"`, `"subagent"` or `{ "agent": "<name>" }`; `by` alone satisfies `tool_called` and `tool_not_called` (so `{ "type": "tool_called", "by": { "agent": "planner" }, "max": 0 }` means the planner made no call), `tool_called` with `first: true` and `by` tests that agent's first call, and `first_message` and `final_message` with `by` read that agent's text. `by` needs the new capability `childCalls` (matchers, skill checks) or `childText` (text checks), and a harness without it makes the case not applicable. Claude Code declares both. Changed on purpose: `first_message` and `final_message` now read the main agent only, which a subagent's flattened text no longer satisfies; a `tool_called` with `max: 0` and no `min` now defaults `min` to 0 (it could never pass before); `"by" is not yet supported` is gone, so a bad `by` is a load error that says what it must be. Run records gain `agent` on each tool call, and skill events carry one. `ToolCall.agent` is now always set. A negative claim about `{ "agent": "X" }` (`tool_not_called`, `tool_called` with a count of 0, `skill_not_loaded`, `transcript_lacks`, `tool_output_lacks`) scores 0 with `no agent of type X ran` when no event belongs to an agent of that type; `{ "agent": "main" }` is a load error. New example: `examples/cases/by-agent`.
- Fix: a skill load is now an event with a mechanism and a position, and only a real load of the loaded subject's skill counts. 0.0.1 counted any tool input that mentioned `skills/<name>/SKILL.md`, so a `grep` across the skills, a listing, a fixture in the workspace, or a no-skills run that called the skill tool with a name all scored as loads. Now `skill_loaded` counts a skill-tool call, a read-kind call of the subject's own `SKILL.md`, and a shell command that `cat`s, `head`s, `tail`s, `less`es, `bat`s, `nl`s or `sed -n`s it (path resolved to the run's copy of the subject or a placed skill copy; a path in the workspace never counts). This is the one change to what a 0.0.1 suite scores. To keep the old rule for one release, run with `--lenient`: a `skill_loaded` or `skill_not_loaded` with neither `via` nor `resolved` then counts any input that mentions `skills/<name>/SKILL.md`. New fields `via` (`skill_tool`, `file_read`, `shell_read`, or a list; `injected` is reserved) and `resolved` on both; new checks `skill_available` and `skill_not_available` (they read the harness's own listing and need `skillListing`) and `skill_file_read` (`skill` and a `path` glob relative to the skill's directory, for `references/*.md` and the like). Run records gain `skillEvents` beside `skillsLoaded`, which is now the sorted names of the `load` events. `Harness` gained the required `pathOf(call)`, which returns the file a read call targets, so an adapter outside this package must add it. New examples: `examples/cases/skill-available` and `examples/cases/skill-file-read`.
- Every run now loads a copy of the subject, never the subject itself. A directory is copied and a git ref is exported with `git archive` (so `export-ignore` applies, and there is no worktree). The copy leaves out `.git`, `node_modules`, the cases directory and the output directory when they are inside the subject, and every glob in the new `subjectExclude` config key. A directory that only held excluded paths is left out too, and so is the project's config file. A link in the subject that points outside it, through any chain of links, is a load error, and so is a cases directory that is or contains the subject. Each run gets a fresh copy, so one run's edits never reach the next or your checkout. The run record has `subjectMutated` and `subjectChanges`, the new check `subject_unchanged` scores 1 when the agent changed nothing, and a subject directory that changed while the command ran makes it exit 1 with the paths. Migration: a hook that depends on its absolute path or on `.git` sees the copy instead.
- The harness now starts with an allowlisted environment instead of a copy of yours. It gets `PATH`, `SHELL`, `USER`, `LOGNAME`, `TMPDIR`, `TERM`, `TZ`, `LANG`, `LANGUAGE`, `LC_*`, the proxy and certificate variables, its own adapter's login variables, and the names listed in the new `env` config key; the judge gets the same. Migration: a harness that needs a variable outside the allowlist needs it named in `env`.
- An unknown key in a `case.json` is now a load error that names the key and the keys that are allowed. Keys that start with `x-` are kept and written to `results.json`. `--lenient` (or `lenient` in the config file) drops unknown keys with a warning, for one release. Every field of a check has a type, and the reference page lists it. Validation is stricter in two small ways: a `flags` that is not valid now fails at load even when no regular expression is beside it, and when a file has several faults, an unknown-key error is reported before the others.
- The help text is written from the same tables that parse the command line. It lists the commands, then every flag once with its default and the commands that take it. No command, flag, or default changed.
- The documentation is a website next to the landing page. Its reference pages for the checks, the commands and flags, the config file, the harnesses, and the API are generated from the code, and the tests fail when a committed page or a documented example no longer matches the tool.
- Each harness adapter now declares what it can observe or do, and a case that needs more is reported "not applicable" on that harness: no runs, no score, a line in the report, never a pass and never a failure. A case or a check takes `requires` (capability names, or `bin:<name>` for an executable on `PATH`), a check takes `ifUnsupported: "skip"` to be dropped instead, and a case takes `harnesses` with a `note`. `results.json` gains `notApplicable`, `skippedChecks`, `commonSet`, and `applicable` and `total` on each suite. Migration: the suite line of the report now ends with `(n of N cases)`, and the command exits 2 with `no case applies to <harness>` when nothing applies. The new Capabilities page of the docs lists the names.
- Releases are guarded. `scripts/release-plan.sh` refuses a version tag that does not match `package.json`, is not on `main`, has no changelog entry, or is not above the latest version on npm, and the `Release check` workflow runs the same guards on every pull request. The publish workflow also makes the GitHub release.
- `--isolated` (config key `isolated`) starts the harness with nothing loaded but the subject, and proves it from what the harness reports: the run record has the new fields `isolated`, `loaded`, `reportMissing`, `judgeProblem` (plugins, skills, agents, rules, hooks, MCP servers; null where the harness does not report that kind) and `unexpected`, and under `--isolated` a run that loaded anything outside the subject, or whose harness did not report what it loaded, is invalid with `loaded outside the subject: <names>` or `the harness did not report what it loaded`. The judge is held to the same rule. Only Claude Code takes it (it gets `--setting-sources user` and `--strict-mcp-config`, never `--bare`); another harness, Pi included, is a usage error that names it, because `--isolated` needs the harness to prove what it loaded. Organization-managed plugins cannot be switched off, so they invalidate the run; managed policy settings, a managed CLAUDE.md, rules and hooks are not covered by the report. Claude Code also gets `CLAUDE_CODE_DISABLE_POLICY_SKILLS=1` and `CLAUDE_CODE_DISABLE_ORG_MEMORY=1`, and the judge harness must take `--isolated` too. Skills that a claude.ai login syncs into the run's home are found from the files they leave and reported as `account skill <name>`. The CI guide recommends it. Subject-loaded validation now runs for every adapter that declares `loadedReport`.
- Cases can be nested and selected. A case is a directory with a `prompt.md` or a `case.json` at any depth under the cases directory, and its id is its path with `/`. A directory whose name starts with `_` is skipped with everything under it, so a 0.0.1 case directory whose name starts with `_` stops being a case. Nothing under a case is searched, and an `@` or `,` in a directory name of a case id is a load error, as is a `case.json` with no `prompt.md`. `--case` takes globs (`*` within one directory, `**` across directories, `?`, `{a,b}`) and can be repeated or comma-separated; `--not-case`, `--tag`, `--tag-all` and `--not-tag` select by id and by the new `tags` key, on `run`, `score` and `list`. A 0.0.1 `--case` value whose only special character is `*` matches what it matched, but `*` no longer crosses `/`. Changed on purpose: `?`, `{`, `}` and `\` in the value are now glob syntax, and `,` separates values. New case keys: `tags`, `description`, `targets`, `kind`, `expected`, `guard`, `reps`, `model`, `judgeModel`, `env` (names `CASE_*`, `TZ`, `LANG`, `LC_ALL`, set for the agent) and `minDelta`. A case's `reps`, `model` and `judgeModel` win over the flags. `results.json` `caseMeta` gains `tags`, `targets`, `guard`, `kind`, `description`, `reps`, `model`, `judgeModel` and `env`. The report lists guard cases in their own table and ends with a coverage table of target skills, which `list --targets` also prints. `Case` gained required fields (`tags`, `targets`, `guard`, `env`), which affects code that builds `Case` literals. New guide: Organise a suite.
- Cases can have variants. A `variants` list in `case.json` puts the prompt a different way without a copy of the case: each variant has an `id` (lowercase letters, digits and hyphens), exactly one of `prompt` (the whole prompt) and `promptAppend` (added to `prompt.md` after a blank line), optional `tags` (added to the case's tags for that variant) and `heldout`. A variant runs as `<case id>@<variant id>`, and a case with variants never runs bare. `--case` and `--not-case` match a variant by its full id or its case's id. A case whose variants all set `prompt` needs no `prompt.md`. A variant with `heldout: true` runs only with the new `--heldout` switch of `run`, `score` and `list`; the coverage table's `held-out` column counts them. `results.json` `caseMeta` is keyed by the full id and gains `base`, `variant` and `heldout`. A `--case` glob with an `@` reads only the cases that the part before the `@` reaches, and an empty `prompt.md` is fine when every variant has its own `prompt`. A `weight` of `null` is accepted by the schemas too. `Case` gained required fields `base`, `variant` and `heldout`, and `loadCases` returns every variant, held-out ones included. New example: `examples/cases/variants/commit-help`.
- The package ships JSON Schemas for `case.json` and `skill-evals.config.json` in `schema/`, written from the same tables the loader reads, and the tests fail when a committed schema differs. A `"$schema"` key (a string, ignored by the tool) is now allowed in both files so that an editor can use them.
- `skill-evals --help`, `skill-evals help`, `skill-evals help <command>` and `skill-evals <command> --help` print the help on standard output and exit 0; `--help` wins over every other flag, and `help <unknown>` exits 2. A bare command line and an unknown command still print the usage on standard error and exit 2. New command `validate` checks a suite with no model spend and reports every problem at once: each case that does not load is a problem (exit 2), and a `targets` or check `skill` name the subject lacks, or a case an installed harness would not run, is a warning (exit 0). `loadCases` gained the option `onError`, which collects load errors instead of throwing.
- Tool checks can count, order and pick the first action. One matcher shape (`kind`, `name`, `inputMatches`, `flags`) describes a call everywhere: `tool_called` gains `min` (default 1), `max`, `sameTurn` and `first`, `tool_not_called` is the same check with `max: 0`, the new `tool_order` takes `before` and `after` (each a matcher with `which: "first" | "last"`) or a `sequence` with `strict`, and the new `first_tool` takes `matches` and `ignoring`. `skill_loaded` gains `anyOf`, `first` and `ignoring`, and one rule now finds skill loads with their position in the call list; a `skill_loaded` with only `skill` scores as before. A failing check puts the calls around the failure in its reason. `sameTurn` needs the new capability `turnGrouping`, which only Claude Code declares: each tool call has a `turn` (one per assistant message), and elsewhere the case is not applicable. `ToolCall` gained the optional `index` and `turn`, set on new records and absent on 0.0.1 ones (`agent` is typed too, and no adapter sets it yet). `sameTurn` means every matching call was issued in one turn. These checks see every call, a subagent's included, until subagent attribution lands. A matcher with `by` or `inputLinesMax` is a load error that says it is not yet supported. New examples: `examples/cases/tool-order` and `examples/cases/first-tool`.
- File checks look at what the agent changed. The workspace is hashed after it is copied and before the harness starts (the home just before the prompt runs, after the login files and skill copies), the run record gains `changedFiles` (`created`, `modified`, `deleted`), and `Outcome` gains `seed`, `changed`, `home`, `homeSeed` and `homeChanged`. New checks: `file_absent`, `file_lacks`, `file_unchanged`, `file_changed`, `files_changed_only` (`allow`, `ignore`), `file_count` (`min` default 1, `max`), `dir_exists` and `file_lines` (`min`, `max`); `file_exists` gains `created`, `file_matches` and `file_lacks` take `quantifier` (`any` and `all`), and every file check takes `root` (`workspace` or `home`). A `path` that contains `*`, `?` or `{` is now a glob (`*` and `?` within a directory, `**` across, `{a,b}`), so a 0.0.1 `file_exists` or `file_matches` with a plain path scores as before, and one whose path held those characters is now read as a glob. A glob never follows a link, a path through a link that leaves the root counts as absent, a glob that matches more than 5000 paths scores 0 with the glob named, files are read as UTF-8 with replacement characters, and a file over 5 MB scores 0 in a pattern check. `inputLinesMax` now works in a matcher and on `tool_called` and `tool_not_called`: the call's input, in its longest string value, has at most that many lines (`by` is still rejected). New examples: `examples/cases/file-state`.
- File checks, round two. A plain `path` that names a directory, or ends in `/`, means every file under it for `file_absent`, `file_lacks`, `file_unchanged`, `file_changed`, `file_count`, `file_lines` and the `allow` and `ignore` of `files_changed_only` (`file_exists`, `file_matches` and `dir_exists` keep reading it as one entry, and `file_exists` on a file that cannot be read scores 0 again). A directory that cannot be listed, before or after the run, makes the checks that depend on listing score 0 and name it. The workspace of a case is copied with its links unchanged, so a link inside it stays relative, and a link in a case's `workspace/` that is absolute or leaves it is a load error. A `path` that starts with `./` is a load error. A matcher takes `inputLinesMin` beside `inputLinesMax` (a call matches when its longest string value has at least that many lines), so `{ "type": "tool_not_called", "kind": "write", "inputLinesMin": 1001 }` says no single write was longer than 1000 lines; `inputLinesMin` above `inputLinesMax` is a load error. The new `validate` lint warns about a `file_unchanged` path that matches nothing in the case's `workspace/`. Files are hashed in 1 MiB chunks. `Outcome` gains `unlisted` and `homeUnlisted`.
- New check `command` runs a shell command in the workspace after the agent exits: the project's own checks, a held-out check the agent never saw, a mutation check, or a `git` query. It takes `run`, `expectExit` (default 0), `stdoutMatches`, `stdoutLacks`, `flags`, `timeoutSeconds` (default 120) and `scoreFrom` (`exit`, the default, or `stdout`, which reads a number from 0 to 1 from the last non-empty line of standard output). A `grader/` folder beside `prompt.md` is never copied into the workspace; after the agent exits it is copied into a new temp directory that `SKILL_EVALS_GRADER_DIR` names, and a `grader/` inside `workspace/` is a load error. The command runs as you, without a sandbox, with only `PATH`, `TMPDIR`, `LANG`, the throwaway `HOME`, `SKILL_EVALS_WORKSPACE`, `SKILL_EVALS_GRADER_DIR`, `SKILL_EVALS_SEED_DIR` (a copy of the workspace before the agent ran, taken only when a case has a `command` check), `SKILL_EVALS_HOME`, fixed `GIT_*` variables and the case's `env`; it never gets a provider key. Commands run in case order, and a command that times out or cannot start scores 0 and leaves the run valid. On an invalid run they are not run, and the run's first reason stays. The run record keeps `command` (`run`, `exit`, `durationMs`, `stdout`, `stderr`; each stream cut to its last 2,000 bytes) on the check, beside the check's own `scoreFrom` setting. Commands run after every other check is scored (the record keeps the case's order). Each stream is capped at 5 MB while it is read, and a rule that throws scores its check 0 with `the check could not be scored: <message>`. The seed copy is read-only and verified before each command, the harness's login files are removed from the home before the first command, and a process that left the command's process group cannot hold the check past a short drain. `exec` kills the process group when the agent exits. A throw while a run is scored becomes an invalid record (`the run could not be scored: <message>`) instead of ending the suite, and one failing cleanup at exit no longer stops the others. A `Rule` may now return a promise, `checkScore` returns `Verdict | Promise<Verdict>`, `Outcome` gains `command`, and `Case` gains `graderDir`. New example: `examples/cases/command`. New section on the safety page.
- Cases can set up their workspace. New case keys: `setup` (steps that run in the workspace before the agent starts: `{ "run", "timeoutSeconds" }`, default 60 seconds, or `{ "git": { "init", "branch", "commitAll", "remote" } }`, which expands to `git init -q -b <branch>`, `git add -A && git commit -q -m <commitAll>` and a bare remote with a push), `home` (a folder of the case copied into the throwaway home after the login files and skill copies; a file at a harness's login path is a load error) and `fixtures` (shared folders layered into the workspace in order before `workspace/`; each must exist and stay inside the cases folder). A case's `fixture/` folder is never copied into the workspace: setup sees it as `$SKILL_EVALS_FIXTURE_DIR`, and it is removed afterwards. `$SKILL_EVALS_REMOTE_DIR`, a per-run temp directory outside the workspace, holds bare remotes and linked worktrees and reaches command checks too. Setup runs as you with the command-check environment (git configuration off, fixed author), and never gets the grader or seed directory. A failed step means the harness never starts and the run is invalid (`setup failed: step <n> (...)`). The workspace seed and `$SKILL_EVALS_SEED_DIR` are now taken after setup. Links in `fixture/`, `home/` and shared fixtures follow the `workspace/` rule. `Case` gained required fields `setup`, `fixtureDirs`, `fixtureDir` and `homeDir`, and `workspaceDir` is no longer an option of the internal session. Setup commits as `Developer <developer@example.com>`, and a case `env` may set the six `GIT_AUTHOR_*` and `GIT_COMMITTER_*` name, email and date variables for setup, the agent and commands; `GIT_OPTIONAL_LOCKS=0` and `GIT_CEILING_DIRECTORIES` (the workspace's parent) are set for setup and commands. A `fixtures` or `home` folder that is, holds or sits inside a case folder or a case's `grader/` or `fixture/` is a load error, and a `home` file that would replace a file the harness placed makes the run invalid. Migration: a 0.0.1 case with a stray file named `fixture`, or a `fixture/` folder holding a link that leaves it, is now a load error. New examples: `examples/cases/setup-git`, `setup-home` and `shared-fixture`.
- Every adapter now emits one normalized per-run transcript: the assistant's text between tool calls, each tool call, and each tool result, in order. It is written whole to `<label><rep>.transcript.json` next to the stream file before any check runs, and the run record gains `transcriptFile` (relative to the output directory; `results.json` `toolCalls` still keep inputs and no outputs). Command checks get the absolute path in `SKILL_EVALS_TRANSCRIPT`. `Parsed` gained `transcript` and `sessionId` (set for Claude Code, Pi, Codex and OpenCode), and `toolCalls` is always derived from the transcript. Streams are decoded as UTF-8 with replacement, so invalid bytes never fail a run, and `bytes` records the size of the text as decoded; the copy for a judge cuts any text or output over 20,000 bytes and sets `truncated`. Claude Code, Codex, OpenCode and Pi now declare `assistantText` and `toolOutputs`, OpenCode also `toolDurations`, and `turnGrouping` is now declared by Claude Code, Pi and OpenCode (Pi counts `turn_end` events, OpenCode `step_start` events); Cursor declares nothing until it is verified. A tool result exists only where the stream carries one: a Codex item with no result, and a Pi `tool_execution_end` with no `result`, give no output. `ToolCall` gains `durationMs` from its result, and a matcher or a `tool_called`, `tool_not_called` check takes `minDurationMs` and `maxDurationMs` (positive integers, `min` not above `max`; they need `toolDurations`). A skill-tool call whose tool result was an error is no longer resolved where the adapter has `toolOutputs`. `Harness.parse` results must now carry `transcript` and `sessionId`, which affects an adapter outside this package. New page: The transcript.
- Checks on what the agent said and what its tools returned, built on the transcript. `transcript_matches` and `transcript_lacks` take `pattern`, `flags`, `where` (`assistant_text`, the default, `tool_input`, `tool_output` or `all`) and `scope` (`any`, the default, `first_message`, `final_message`, `{ "before": matcher }`, `{ "after": matcher }`, or `{ "first_message": true, "before": matcher }`). `first_message` is the main agent's first non-empty text, wherever it falls, not the text before the first tool call; the bounded form scores 0 when that text comes after the matcher's first call. `before` and `after` cut at the first matching call, and no match scores 0 with the matcher named. `by` is a load error that says it is not yet supported, in every mode. `tool_output_matches` and `tool_output_lacks` take `tool` (a matcher), `pattern`, `flags` and `which` (`first`, `last` or `any`, the default): the output is the tool's own result, a call with no result does not match, and `tool_output_lacks` fails closed for one. `tool_output_size` takes `maxBytes` and an optional `tool`. The text checks need `assistantText` (or `toolOutputs` for `tool_output` and `all`), the output checks need `toolOutputs`. Patterns run on the first 1,000,000 characters of an event. `Outcome` gains `transcript`, which affects code that builds an `Outcome`. New examples: `examples/cases/transcript-matches` and `examples/cases/tool-output-matches`.

## 0.0.1

The first release. The runner comes from the `evals/` folder of [magic](https://github.com/PhillipChaffee/magic), where it scored that one set of skills.

- Run it in any project. The project is the git repository that holds the working directory, and the cases default to `evals/cases` in it.
- Score a plugin, a plain folder of skills, or `none`, which loads no skills and is the baseline for a comparison.
- Set defaults in an optional `skill-evals.config.json`.
- Use it from code with `evaluate`, `loadCases`, and `HARNESSES`.
- A prompt that starts with a dash reaches the agent in every harness.
- Windows is not supported.
- The package is written in TypeScript. It ships compiled JavaScript and type declarations, and still has no dependencies.

- A `decision` check asks a decision model a question about the final answer. The case sets what each allowed answer is worth, the model returns a probability for each answer, and the check's score is the expected value. All decision checks of a case go out in one request for each run.
- `--decision-model` and `--decision-url`, and `decisionModel` and `decisionUrl` in the config file, set the model and its endpoint. The client speaks Baseten's System One API and reads its key from `BASETEN_API_KEY`. It was written from the API's documentation. It has scored checks against bison-1 on a self-hosted deployment, and has not yet called Baseten's hosted API.
- `--decision-timeout <seconds>` and `decisionTimeout` in the config file set how long one request to the decision model may take. The default stays 60 seconds. A cold start of a self-hosted model can take that long.
- A decision reply whose probabilities were rounded to 6 decimals is accepted. The sum over the allowed answers may differ from 1 by 0.0000005 for each answer, where the limit was 0.000001 in total, which rejected three honest options that added up to 0.999999.
