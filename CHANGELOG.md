# Changelog

## Unreleased

- Every run now loads a copy of the subject, never the subject itself. A directory is copied and a git ref is exported with `git archive` (so `export-ignore` applies, and there is no worktree). The copy leaves out `.git`, `node_modules`, the cases directory and the output directory when they are inside the subject, and every glob in the new `subjectExclude` config key. A directory that only held excluded paths is left out too, and so is the project's config file. A link in the subject that points outside it, through any chain of links, is a load error, and so is a cases directory that is or contains the subject. Each run gets a fresh copy, so one run's edits never reach the next or your checkout. The run record has `subjectMutated` and `subjectChanges`, the new check `subject_unchanged` scores 1 when the agent changed nothing, and a subject directory that changed while the command ran makes it exit 1 with the paths. Migration: a hook that depends on its absolute path or on `.git` sees the copy instead.
- The harness now starts with an allowlisted environment instead of a copy of yours. It gets `PATH`, `SHELL`, `USER`, `LOGNAME`, `TMPDIR`, `TERM`, `TZ`, `LANG`, `LANGUAGE`, `LC_*`, the proxy and certificate variables, its own adapter's login variables, and the names listed in the new `env` config key; the judge gets the same. Migration: a harness that needs a variable outside the allowlist needs it named in `env`.
- An unknown key in a `case.json` is now a load error that names the key and the keys that are allowed. Keys that start with `x-` are kept and written to `results.json`. `--lenient` (or `lenient` in the config file) drops unknown keys with a warning, for one release. Every field of a check has a type, and the reference page lists it. Validation is stricter in two small ways: a `flags` that is not valid now fails at load even when no regular expression is beside it, and when a file has several faults, an unknown-key error is reported before the others.
- The help text is written from the same tables that parse the command line. It lists the commands, then every flag once with its default and the commands that take it. No command, flag, or default changed.
- The documentation is a website next to the landing page. Its reference pages for the checks, the commands and flags, the config file, the harnesses, and the API are generated from the code, and the tests fail when a committed page or a documented example no longer matches the tool.
- Each harness adapter now declares what it can observe or do, and a case that needs more is reported "not applicable" on that harness: no runs, no score, a line in the report, never a pass and never a failure. A case or a check takes `requires` (capability names, or `bin:<name>` for an executable on `PATH`), a check takes `ifUnsupported: "skip"` to be dropped instead, and a case takes `harnesses` with a `note`. `results.json` gains `notApplicable`, `skippedChecks`, `commonSet`, and `applicable` and `total` on each suite. Migration: the suite line of the report now ends with `(n of N cases)`, and the command exits 2 with `no case applies to <harness>` when nothing applies. The new Capabilities page of the docs lists the names.
- Releases are guarded. `scripts/release-plan.sh` refuses a version tag that does not match `package.json`, is not on `main`, has no changelog entry, or is not above the latest version on npm, and the `Release check` workflow runs the same guards on every pull request. The publish workflow also makes the GitHub release.
- `--isolated` (config key `isolated`) starts the harness with nothing loaded but the subject, and proves it from what the harness reports: the run record has the new fields `isolated`, `loaded`, `reportMissing`, `judgeProblem` (plugins, skills, agents, rules, hooks, MCP servers; null where the harness does not report that kind) and `unexpected`, and under `--isolated` a run that loaded anything outside the subject, or whose harness did not report what it loaded, is invalid with `loaded outside the subject: <names>` or `the harness did not report what it loaded`. The judge is held to the same rule. Only Claude Code takes it (it gets `--setting-sources user` and `--strict-mcp-config`, never `--bare`); another harness, Pi included, is a usage error that names it, because `--isolated` needs the harness to prove what it loaded. Organization-managed plugins cannot be switched off, so they invalidate the run; managed policy settings, a managed CLAUDE.md, rules and hooks are not covered by the report. Claude Code also gets `CLAUDE_CODE_DISABLE_POLICY_SKILLS=1` and `CLAUDE_CODE_DISABLE_ORG_MEMORY=1`, and the judge harness must take `--isolated` too. Skills that a claude.ai login syncs into the run's home are found from the files they leave and reported as `account skill <name>`. The CI guide recommends it. Subject-loaded validation now runs for every adapter that declares `loadedReport`.
- Cases can be nested and selected. A case is a directory with a `prompt.md` or a `case.json` at any depth under the cases directory, and its id is its path with `/`. A directory whose name starts with `_` is skipped with everything under it, so a 0.0.1 case directory whose name starts with `_` stops being a case. Nothing under a case is searched, and an `@` or `,` in a directory name of a case id is a load error, as is a `case.json` with no `prompt.md`. `--case` takes globs (`*` within one directory, `**` across directories, `?`, `{a,b}`) and can be repeated or comma-separated; `--not-case`, `--tag`, `--tag-all` and `--not-tag` select by id and by the new `tags` key, on `run`, `score` and `list`. A 0.0.1 `--case` value whose only special character is `*` matches what it matched, but `*` no longer crosses `/`. Changed on purpose: `?`, `{`, `}` and `\` in the value are now glob syntax, and `,` separates values. New case keys: `tags`, `description`, `targets`, `kind`, `expected`, `guard`, `reps`, `model`, `judgeModel`, `env` (names `CASE_*`, `TZ`, `LANG`, `LC_ALL`, set for the agent) and `minDelta`. A case's `reps`, `model` and `judgeModel` win over the flags. `results.json` `caseMeta` gains `tags`, `targets`, `guard`, `kind`, `description`, `reps`, `model`, `judgeModel` and `env`. The report lists guard cases in their own table and ends with a coverage table of target skills, which `list --targets` also prints. `Case` gained required fields (`tags`, `targets`, `guard`, `env`), which affects code that builds `Case` literals. New guide: Organise a suite.
- Cases can have variants. A `variants` list in `case.json` puts the prompt a different way without a copy of the case: each variant has an `id` (lowercase letters, digits and hyphens), exactly one of `prompt` (the whole prompt) and `promptAppend` (added to `prompt.md` after a blank line), optional `tags` (added to the case's tags for that variant) and `heldout`. A variant runs as `<case id>@<variant id>`, and a case with variants never runs bare. `--case` and `--not-case` match a variant by its full id or its case's id. A case whose variants all set `prompt` needs no `prompt.md`. A variant with `heldout: true` runs only with the new `--heldout` switch of `run`, `score` and `list`; the coverage table's `held-out` column counts them. `results.json` `caseMeta` is keyed by the full id and gains `base`, `variant` and `heldout`. A `--case` glob with an `@` reads only the cases that the part before the `@` reaches, and an empty `prompt.md` is fine when every variant has its own `prompt`. A `weight` of `null` is accepted by the schemas too. `Case` gained required fields `base`, `variant` and `heldout`, and `loadCases` returns every variant, held-out ones included. New example: `examples/cases/variants/commit-help`.
- The package ships JSON Schemas for `case.json` and `skill-evals.config.json` in `schema/`, written from the same tables the loader reads, and the tests fail when a committed schema differs. A `"$schema"` key (a string, ignored by the tool) is now allowed in both files so that an editor can use them.

## 0.0.1

The first release. The runner comes from the `evals/` folder of [magic](https://github.com/PhillipChaffee/magic), where it scored that one set of skills.

- Run it in any project. The project is the git repository that holds the working directory, and the cases default to `evals/cases` in it.
- Score a plugin, a plain folder of skills, or `none`, which loads no skills and is the baseline for a comparison.
- Set defaults in an optional `skill-evals.config.json`.
- Use it from code with `evaluate`, `loadCases`, and `HARNESSES`.
- A prompt that starts with a dash reaches the agent in every harness.
- Windows is not supported.
- The package is written in TypeScript. It ships compiled JavaScript and type declarations, and still has no dependencies.

- A `decision` check asks a decision model a question about the final answer. The case sets what each allowed answer is worth, the model returns a probability for each answer, and the check's score is the expected value. All decision checks of a case go out in one request for each run.
- `--decision-model` and `--decision-url`, and `decisionModel` and `decisionUrl` in the config file, set the model and its endpoint. The client speaks Baseten's System One API and reads its key from `BASETEN_API_KEY`. It was written from the API's documentation. It has scored checks against bison-1 on a self-hosted deployment, and has not yet called Baseten's hosted API.
- `--decision-timeout <seconds>` and `decisionTimeout` in the config file set how long one request to the decision model may take. The default stays 60 seconds. A cold start of a self-hosted model can take that long.
- A decision reply whose probabilities were rounded to 6 decimals is accepted. The sum over the allowed answers may differ from 1 by 0.0000005 for each answer, where the limit was 0.000001 in total, which rejected three honest options that added up to 0.999999.
