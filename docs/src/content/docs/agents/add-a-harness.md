---
title: Add a harness
description: The steps to add an adapter for another coding agent.
---

Adapters live in this package. Loading one from your own code is not supported yet.

1. Add `src/harnesses/<id>.ts` whose default export has the required fields of the `Harness` type in [`src/harnesses/shared.ts`](https://github.com/PhillipChaffee/skill-evals/blob/main/src/harnesses/shared.ts): `id`, `bin`, `authFiles`, `authEnv`, `capabilities`, `status`, `invocation`, `pathOf`, `parse`. The optional fields are `skillOf`, `placedAfterSetup`, `foreign`, `isolation`, `isolationGap` and `strays`. Declare the stream events that `parse` reads as a type in the same file.
2. In `invocation`, load a plugin subject the way the harness loads a local plugin (`pluginDir`), copy a skills subject to where the harness discovers a user's skills (`placeSkills`), and point the harness's own config variables into `home`. Return `setup` commands when the harness has to install the plugin before it runs. When `subject` is `null`, load nothing. The judge and the `none` baseline run that way.
3. Pass the prompt so that a leading dash cannot be read as a flag: after a `--` separator, or in `stdin` when the CLI has no separator. Confirm it against the real CLI.

   When the harness exits, the run stops every other process of its process group, and a process outside the group cannot keep the run waiting. Output that another process writes to the harness's standard output after the harness has exited is not read: the pipes are closed after a 250 ms drain.

4. In `parse`, normalize the stream and nothing more. Return `null` for a field the harness does not report. Put only a tool call's input in `toolCalls`, never its output, or file contents will count as skill loads. Build each tool call with `toolCall` and a table from the harness's tool names to the kinds under [Tool checks](../reference/checks.md#tool-kinds). Give the adapter a `pathOf` that returns the file a `read` call targets from its input (`stringArg(call, ["path"])` when the argument is a string), or `null` for a harness with no read kind: skill-load detection reads paths only through it. If its skill tool names the skill in an argument other than `skill`, `name` or `id`, give it a `skillOf`. If the harness copies a plugin's skills itself during setup, as Codex does into its plugin cache, give it a `placedAfterSetup` that lists those directories once the setup steps have run, so that a read of them counts and a change to them is seen.
5. Add the adapter to `HARNESSES` in `src/harnesses/index.ts` at its place in the preference order.
6. Capture one real stream into `test/fixtures/` and add it to `src/adapters.test.ts`. Add the harness to the table of skill locations in `src/invocation.test.ts`, and add a row to every table in [How each harness is started](how-they-run.md) and [What was verified](verified.md) and to the table of skill locations under [Subjects](../concepts/subjects.md).
7. To run the turns of a [multi-turn case](../guides/multi-turn.md), `invocation` gets `input.session`, the session id that the turn before stated in its stream (`Parsed.sessionId`), and continues that session by the CLI's own flag. Declare `multiTurn` only once you have read that flag in the real CLI's `--help`. Declare `userInvoke` only with a `userInvocation` that returns the CLI's own user syntax for a skill, confirmed the same way. Declare `compact`, `clear` or `resume` only when the CLI's own way of doing it is confirmed; `input.turn.event` is `"compact"` for a harness process that must compact. Declare `askUser` only when the CLI has a tool that asks the user, you have mapped its name to the kind `question` in the adapter's table, and the stream shows its calls; set `Parsed.askedUser` where the stream says the process stopped for input. A harness whose `--help` you could not read stays undeclared, and the case is not applicable there. Every adapter has `history`, because the runner renders a case's `history.json` as a block in front of the first prompt and the adapter only sends `input.prompt`. Declare `historyNative` only with an `installHistory` that writes the history into the CLI's own session store and returns the session id that `invocation` resumes, and `sessionStore` only with an `installSessions` that writes earlier sessions where the CLI lists them. Declare `rules` only with an `installRules` and a `rulesTargets` that put a subject's rule files and instruction file where the CLI reads them, confirmed from the CLI's strings or `--help`, and `hooks` only when the stream states each hook that ran, which the adapter emits as a transcript event of type `hook` (`hookPart`); see [Rules, hooks and preconditions](../guides/rules-hooks-preconditions.md). Read the file layout from the real CLI, never from a guess; Claude Code's is in [the design note](https://github.com/PhillipChaffee/skill-evals/blob/main/docs/design/multi-turn-and-history.md#native-history-and-session-stores-task-25-unconfirmed), and is still unconfirmed against a real run.
