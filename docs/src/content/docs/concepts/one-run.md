---
title: What one run does
description: Every step of a run, and when a run does not count.
---

1. Creates a new, empty home directory and a new workspace directory. The names of these directories and of the subject copy (`home-*`, `proj-*`, `kit-*`) say nothing about why they exist.
2. Copies the case's shared `fixtures` and its `workspace/` folder into the workspace, runs the case's `setup` steps there, seeds the case's `home/` folder into the home after the login files, and copies the export of the subject into a new `kit-*` directory, which the harness loads. See [Subjects](subjects.md).
3. Copies the harness's credential files from your real home into the new home, so a login keeps working. Nothing else is copied.
4. Starts the harness with `HOME` and the XDG directories pointed at the new home, and with the subject loaded as [Subjects](subjects.md) describes. The harness does not get your whole environment, only an allowlist: `PATH`, `SHELL`, `USER`, `LOGNAME`, `TMPDIR`, `TERM`, `TZ`, `LANG`, `LANGUAGE`, every `LC_*`, the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY`, in upper and lower case), and the certificate variables (`SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`). It also gets the login variables of its own adapter, such as `ANTHROPIC_API_KEY` for Claude Code, and every name you list in the `env` key of the [config file](../reference/config.md). When the suite has a decision check, the harness does not get the decision model's API key, even when `env` lists it. Its `TMPDIR` is not yours: each run gets a new temp directory of its own, removed when the run ends.
5. Turns the harness's event stream into one run record and scores the case's checks. A judged check starts one more harness run, described under [Judged checks](../guides/judged-checks.md). The decision checks of the case go to the decision model in one request, described under [Decision checks](../guides/decision-checks.md).
6. Hashes the copy of the subject again, and records what the agent changed in it.
7. Deletes the three directories.

A run counts only when it is valid. A run that hit its `maxTurns` is valid and scored, and so is a timed-out run of a case that sets `onTimeout: "score"`; see [Limits](../guides/write-a-case.md#limits). A run is invalid when it failed (harness error, time limit), when the harness reported what it loaded and the subject was not in it, when `--isolated` is set and the harness reported something loaded that is not the subject, when a judged check or a decision check got no usable score, or when a check's regular expression took longer than 10 s on one text. A pattern is tested against a text of more than 16 KB in a worker thread, so a slow pattern cannot hold up the other runs of the command. Invalid runs are listed under the table, left out of every number, and make the command exit 3 unless `--max-invalid` allows them. The count of valid runs is printed beside every score.

"The subject was not in it" means that a plugin's directory is not among the loaded plugins, or that a skill of a skills folder is not among the listed skills. Only Claude Code reports either. In the other four harnesses a subject that did not load shows up as missing skill loads, not as an invalid run.

Every run record keeps `loaded`: what the harness reported as loaded at startup (plugin directories, skills, agents, rules, hooks and MCP servers; a kind the harness does not report is null), `unexpected`: the names among them that do not come from the subject, and `isolated`. Without `--isolated` they are only recorded and no run is invalidated. With `--isolated` the harness is also started with its isolation switches (see [Harnesses](../agents/harnesses.md)), the judge gets them when its harness can take them, and a run is invalid when `unexpected` is not empty (`loaded outside the subject: <names>`), when the harness should report its plugins and skills and did not (`the harness did not report what it loaded`), or when the judge reports anything loaded.

The report proves only what it lists. A bare skill name is treated as a Claude Code built-in; managed policy skills are switched off. Managed policy settings (hooks, environment, permissions), a managed `CLAUDE.md` file, rules, hooks and managed agents are not in the report, so `--isolated` does not prove they are off.

Skills that an account syncs into the run's home are not in the init event either. The adapter finds them from the files they leave, and they count as `account skill <name>`.
